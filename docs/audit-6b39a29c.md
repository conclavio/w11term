# Code review and defensive security audit

Reviewed commit: `6b39a29c` (main, 2026-11-28). Static analysis only: nothing was built or run for the review itself. Each finding was produced by one reviewer and then re-checked against the code by an independent verifier; `info` items were not verified. Findings marked **fixed** were addressed in the change that added this document; everything else is open. High and medium findings carry full detail; low and info findings carry the scenario and recommendation.

## Fixed with this document

- Elevated instances ignore `W11TERM_DATA_DIR` and `W11TERM_SETTINGS_PATH` outside test builds, so the pinned High-integrity data directory cannot be redirected through the environment.
- Bare modifier keys and key releases no longer snap scrollback to the bottom or clear the mouse selection.
- Host-key algorithms already recorded in `known_hosts` are requested first, so a host known by one key type is not reported as changed.
- Interactive SFTP transfers (file drawer and host groups) use a 24-hour ceiling instead of a 600-second total deadline; per-request timeouts still detect a stalled link.
- Selecting a tab of another profile leaves a maximized window alone.
- The sixel work budget allows a 256-colour palette per band and keeps the rows decoded before the budget runs out.

#### [medium, fixed] Elevated instance honours W11TERM_DATA_DIR, bypassing the pinned High-integrity data directory (known_hosts, profiles, device keys)

`src/keys.rs:28` · ssh-core

**Attacker:** B: same-user process at Medium integrity, victim later runs w11term elevated

**Scenario:** keys::data_dir() returns the W11TERM_DATA_DIR environment value before it checks is_elevated(). A Medium-integrity process persists W11TERM_DATA_DIR=<attacker dir> in HKCU\Environment (user-writable; used to build the environment of same-user elevated processes) or sets it in a shell the user elevates from. In the elevated instance, key_exchange() (src/ssh/transport.rs:1028-1038) resolves known_hosts to <attacker dir>\known_hosts, and default_profiles_path() (src/options.rs:741) resolves to <attacker dir>\profiles.json. That profiles.json can carry a "backend":"local" profile with an arbitrary executable plus "startup_profile", which Options::parse_from auto-selects on an implicit launch (src/options.rs:1385-1396).

**Impact:** Medium-to-High integrity escalation: the attacker's local profile executable starts at High integrity on the next plain elevated launch. Separately, the attacker fully controls host-key trust for the elevated instance (pre-seeded keys or @cert-authority lines, so no TOFU prompt and no mismatch error) and can substitute device keys.

- **README architecture and licence text lag the code; trailing sections are misplaced** (`README.md:1080`, info, open). A new contributor uses the Architecture section as the module map, or a packager uses the License section/NOTICE as the list of vendored code. *Recommendation:* Regenerate the Architecture list from lib.rs/main.rs (one line per module), move the stray paragraphs above License, and add wezterm-surface to NOTICE.

- **build.rs stages shell-integration.ps1 by walking up from OUT_DIR, which assumes build and artifact directories coincide** (`build.rs:9`, info, open). A developer or CI configuration sets Cargo's build.build-dir (intermediate artifacts separate from target-dir). OUT_DIR then lives under the build directory, so `out.ancestors().nth(3)` is not the folder that receives w11term.exe. *Recommendation:* Document the constraint next to the build script, or embed the script with include_str! and write it to the data directory on first use so no staging is needed.
